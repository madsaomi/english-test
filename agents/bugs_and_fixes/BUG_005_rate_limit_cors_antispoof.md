# BUG_005: Нет rate limiting, wildcard CORS в проде, обход анти-спуфинга `tg_user_id`

**Дата обнаружения:** 2026-09-26
**Обнаружено:** аудит проекта (продолжение PLAN-015 → PLAN-017)
**Severity:** 🟠 MEDIUM
**Статус:** ✅ ИСПРАВЛЕНО (PLAN-017)

---

## 1. Симптом

1. **Нет rate limiting ни на одном из 7 эндпоинтов.** Злоумышленник (или просто «школьник» с автоскриптом) мог:
   - тысячи раз вызвать `POST /api/test/start` → каждый вызов создаёт сессию в памяти (`cat_engine.sessions`) → рост RAM до OOM на Railway;
   - спамить `POST /api/test/submit-contact` → каждая заявка порождает **реальные сообщения администратору в Telegram** (карточка + детальный результат) → спам и расход квоты бота.
2. **CORS `*` по умолчанию** (`config.py`): если `ALLOWED_ORIGINS` не задан в Variables Railway, то любой сторонний сайт может отправлять `POST` на наш API (в т.ч. `submit-contact` от имени чужого домена).
3. **Анти-спуфинг `tg_user_id` обходился одной строкой.** Условие было `if payload.tg_init_data and IS_BOT_ENABLED:` — клиент, подделавший `tg_user_id`, мог просто **не отправить** поле `tg_init_data`, и проверка подписи не выполнялась вовсе. В Telegram-карточке и в базе лидов появлялся произвольный (чуждой) Telegram ID.

## 2. Первопричина (Root Cause)

| # | Причина |
|---|---|
| 1 | `main.py` не содержал ни одного middleware ограничения частоты; rate limit считался «не нужным для учебного проекта» |
| 2 | `ALLOWED_ORIGINS` по умолчанию `["*"]`, и в `.env.example` не было предупреждения о риске в проде |
| 3 | Проверка подписи была **опциональной по факту наличия поля**, а не **обязательной при наличии идентификатора** — логическая ошибка в условии (`if A and B` вместо «если передан `tg_user_id`, то `B` обязательно») |
| 4 | Отсутствовали security-чеки в `check_integrity.py` для всех трёх дыр |

## 3. Решение (How Fixed)

| Файл | Изменение |
|---|---|
| `backend/config.py` | Добавлены `RATE_LIMIT_ENABLED`, `RATE_LIMIT_REQUESTS` (60), `RATE_LIMIT_WINDOW_SECONDS` (60) и флаг `IS_CORS_WILDCARD` |
| `backend/main.py` | Middleware `rate_limit_middleware`: sliding-window на **IP + хеш User-Agent** (X-Forwarded-For учитывается), только для мутаций `POST/PUT/PATCH/DELETE` на `/api/*`; ответ **429** + `Retry-After`; чистка протухших бакетов по окну (нет утечки памяти) |
| `backend/main.py` (`lifespan`) | WARNING при `CORS == '*'` с примером продакшен-значения; INFO о включённом лимите; предупреждение о **CGNAT**; WARNING если `EXPORT_API_KEY` не задан |
| `backend/main.py` (`submit-contact`) | Если передан `tg_user_id`, но нет `BOT_TOKEN` → 403; нет `tg_init_data` → 403; невалидная подпись → 403. `tg_user_id` в сессию берётся **только** из подписанных данных |
| `.env.example` | `RATE_LIMIT_*` с пояснением CGNAT и рекомендацией по лимиту; предупреждение про wildcard CORS |
| `agents/testing/test_api_http.py` | Новые тесты: `test_rate_limit_blocks_burst` (10 POST → 429, ровно 10 успешных, GET не лимитируется) и `test_tg_user_id_requires_valid_init_data` (403/403/200). Тесты отключают продовый лимит через `RATE_LIMIT_REQUESTS=100000` в env до импорта |
| `agents/tools/check_integrity.py` | +4 чека: rate limit, анти-спуфинг, CORS-warning, документирование переменных |

## 4. Правила предотвращения

1. **Любая мутация под `/api/` обязана быть покрыта лимитом**; GET/HEAD лимитом не трогаем (проверка, каталог, статика).
2. **Условие проверки подписи строим от идентификатора, а не от наличия подписи:** «если прислано `tg_user_id` → подпись обязательна».
3. **Wildcard CORS в проде — предупреждение в лог**, а не молчание.
4. **Новые middleware/конфиги покрываются integrity-чеком** в разделе 6.
5. **Тесты полного прогона (50 POST подряд) обязаны отключать продовые лимиты** через env до импорта модуля — иначе лимитер режет сам тест.
6. Лимиты по умолчанию задаются **с запасом** относительно нормального темпа (тест ≈3.3 req/мин → лимит 60/мин).

## 5. Известный компромисс

Мобильные операторы используют **CGNAT** — несколько разных учеников могут иметь один IP. При едином лимите на IP теоретически возможен ложный `429`. Смягчено:
- лимит 60/мин (в 18 раз выше нормального темпа);
- ключ включает User-Agent, а не только IP;
- лимит и окно настраиваются через env;
- при фактических жалобах — поднять `RATE_LIMIT_REQUESTS` или перейти на per-session лимиты.

## 6. Ручные шаги в Railway

Рекомендуется задать (иначе в лог будет WARNING):
```ini
ALLOWED_ORIGINS=https://<service>.up.railway.app
RATE_LIMIT_ENABLED=true
RATE_LIMIT_REQUESTS=60
RATE_LIMIT_WINDOW_SECONDS=60
EXPORT_API_KEY=<secrets.token_urlsafe(32)>
DATA_DIR=/app/data
```
